## 1. 개발 개요

본 프로젝트는 단순한 "전남대학교 DB"가 아니라, **전남대학교의 학생 정보와 성적을 관리하는 학사행정 DB**를
목표로 한다. 학과 행정실과 학사관리 담당자가 학생의 소속 학과, 지도교수, 개설 강의, 수강신청,
성적 정보를 일관성 있게 관리할 수 있도록 6개 핵심 개체와 6개 관계를 기반으로 설계하였다.

또한 과제 주제가 단순한 예제 수강신청 DB로 보이지 않도록, 전남대학교 공식 대표 홈페이지의 공개
대학·학부(과) 페이지에서 학과명, 단과대학명, 전화번호 114건을 수집하여 `Dept` 테이블에 반영하였다.
실제 학생 개인정보, 실제 학번, 실제 수강신청 내역, 실제 성적은 공개 데이터가 아니므로 사용하지
않았다. 성능 실험에는 개인정보를 포함하지 않는 CSV 더미 데이터를 사용하였다.

## 3. 개념적 모델링

### 3.1 개체 및 속성 설계

본 프로젝트는 총 6개 개체로 구성된다. `Student`, `Dept`, `Professor`, `Lecture`는 독립적으로 식별 가능한
강한 개체이고, `Enrollment`와 `Grade`는 다른 개체가 존재해야 성립하는 약한 개체로 설계하였다.

| 개체 | 강/약 | 기본키 | 주요 속성 | 중복 가능성 및 설계 근거 |
| --- | --- | --- | --- | --- |
| Student | 강한 개체 | stuid | sname, stu_year, phone, email | 학번은 중복 불가, 이름/학년은 중복 가능, email은 UNIQUE |
| Dept | 강한 개체 | deptid | dname, college, office, tel | 학과명은 UNIQUE, 단과대학/전화번호는 여러 학과가 공유 가능 |
| Professor | 강한 개체 | pid | pname, prof_rank, email, office | 교번은 중복 불가, 이름/직급은 중복 가능, email은 UNIQUE |
| Lecture | 강한 개체 | lid | lname, lnum, credit, semester | 강의명은 분반·학기별 중복 가능, 강의번호로 식별 |
| Enrollment | 약한 개체 | enrollid | enroll_date, status, semester, enroll_type | 학생과 강의가 있어야 성립, 동일 학기 중복 신청은 UNIQUE로 차단 |
| Grade | 약한 개체 | gradeid | score, grade_letter, evaluation_date, remark | 수강신청이 있어야 성립, 수강신청 1건당 성적 1건만 허용 |

### 3.2 실제 데이터와 속성 범위

| 개체 | 실제/더미 데이터 반영 | 데이터 범위 |
| --- | --- | --- |
| Dept | 전남대학교 공식 공개 학과 데이터 반영 | 공식 학과·학부 114건, 더미 호실 101호~214호 |
| Student | 기본 샘플 + CSV 더미 데이터 | 기본 12명, CSV 더미 10,000명 |
| Professor | 기본 샘플 데이터 | 기본 8명 |
| Lecture | 기본 샘플 + CSV 더미 데이터 | 기본 8개, CSV 더미 1,000개 |
| Enrollment | 기본 샘플 + CSV 더미 데이터 | 기본 18건, CSV 더미 50,000건 |
| Grade | 기본 샘플 + CSV 더미 데이터 | 기본 12건, CSV 더미 50,000건 |

### 3.3 관계 차수와 최소 관계대응수

관계 차수와 최소 참여 조건은 실제 테이블의 외래키, NULL 허용 여부, UNIQUE 제약으로 구현하였다.

| 관계 | 의미 | 대응수 | 최소 관계대응수 | 실제 구현 |
| --- | --- | --- | --- | --- |
| belong | 학생은 학과에 소속 | Student N : 1 Dept | Student(1,1), Dept(0,N) | `Student.deptid` NOT NULL FK |
| work_dept | 교수는 학과에 소속 | Professor N : 1 Dept | Professor(1,1), Dept(0,N) | `Professor.deptid` NOT NULL FK |
| tutor | 교수가 학생을 지도 | Professor 1 : N Student | Professor(0,N), Student(0,1) | `Student.advisor_pid` NULL 허용 FK |
| manage | 교수가 강의를 담당 | Professor 1 : N Lecture | Professor(0,N), Lecture(1,1) | `Lecture.pid` NOT NULL FK |
| study | 학생이 강의를 수강 | Student M : N Lecture | Student(0,N), Lecture(1,N) | `Enrollment` 교차 릴레이션 |
| evaluate | 수강신청에 성적 부여 | Enrollment 1 : 1 Grade | Enrollment(0,1), Grade(1,1) | `Grade.enrollid` FK + UNIQUE |

### 3.4 카디널리티가 데이터에 반영된 방식

| 설계 조건 | 데이터/제약 반영 |
| --- | --- |
| 학생은 반드시 하나의 학과에 소속 | `Student.deptid NOT NULL`, FK 오류로 없는 학과 입력 차단 |
| 지도교수는 선택 사항 | `Student.advisor_pid`는 NULL 허용 |
| 한 강의는 반드시 한 교수가 담당 | `Lecture.pid NOT NULL` |
| 학생과 강의는 M:N | 학생 1명이 여러 강의를 수강하고, 강의 1개에 여러 학생이 연결되도록 `Enrollment` 사용 |
| 같은 학기 같은 강의 중복 신청 금지 | `UNIQUE(stuid, lid, semester)` |
| 성적은 수강신청에 종속 | `Grade.enrollid`가 `Enrollment.enrollid`를 참조 |
| 수강신청 1건당 성적 최대 1건 | `Grade.enrollid UNIQUE` |

[캡처 삽입 위치: 최종 ERD 이미지. 6개 테이블, PK/FK, Enrollment를 통한 M:N 해소, Grade 1:1 관계가 보이도록 삽입]

## 4. 논리적 모델링

### 4.1 관계 스키마

개념 모델을 다음 관계 스키마로 변환하였다.

```text
Dept(deptid, dname, college, office, tel)
Professor(pid, pname, prof_rank, email, office, deptid(FK))
Student(stuid, sname, stu_year, phone, email, deptid(FK), advisor_pid(FK))
Lecture(lid, lname, lnum, credit, semester, pid(FK))
Enrollment(enrollid, stuid(FK), lid(FK), enroll_date, status, semester, enroll_type)
Grade(gradeid, enrollid(FK), score, grade_letter, evaluation_date, remark)
```

### 4.2 관계별 외래키 삽입 근거

| 관계 | 매핑 결과 | FK 삽입 이유 |
| --- | --- | --- |
| R1 belong | `Student.deptid -> Dept.deptid` | N:1 관계는 N쪽에 외래키를 둔다. 학생은 반드시 학과가 필요하므로 NOT NULL |
| R2 work_dept | `Professor.deptid -> Dept.deptid` | 교수 N:1 학과 관계를 표현하기 위해 Professor에 FK 삽입 |
| R3 tutor | `Student.advisor_pid -> Professor.pid` | 교수 1:N 학생 관계이므로 N쪽 Student에 FK 삽입, 지도교수 미배정 가능 |
| R4 manage | `Lecture.pid -> Professor.pid` | 교수 1:N 강의 관계이므로 Lecture에 FK 삽입, 담당 교수 없는 강의 방지 |
| R5 study | `Enrollment.stuid`, `Enrollment.lid` | Student-Lecture M:N 관계는 직접 FK 하나로 표현할 수 없어 교차 릴레이션으로 분해 |
| R6 evaluate | `Grade.enrollid -> Enrollment.enrollid` | Enrollment-Grade 1:1 관계를 FK + UNIQUE로 구현 |

### 4.3 삭제 및 갱신 규칙

| FK | ON DELETE | ON UPDATE | 설계 의도 |
| --- | --- | --- | --- |
| fk_prof_dept | RESTRICT | CASCADE | 교수가 남아 있는 학과 삭제 방지 |
| fk_stu_dept | RESTRICT | CASCADE | 학생이 남아 있는 학과 삭제 방지 |
| fk_stu_advisor | SET NULL | CASCADE | 교수 삭제 시 학생 데이터는 보존하고 지도교수만 미배정 처리 |
| fk_lec_prof | RESTRICT | CASCADE | 담당 교수가 있는 강의 보호 |
| fk_enr_stu | CASCADE | CASCADE | 학생 삭제 시 종속 수강신청 삭제 |
| fk_enr_lec | CASCADE | CASCADE | 강의 삭제 시 종속 수강신청 삭제 |
| fk_grade_enr | CASCADE | CASCADE | 수강신청 삭제 시 종속 성적 삭제 |

### 5.1 `schema.sql` 구현 설명

| 구현 요소 | 코드 반영 |
| --- | --- |
| DB 생성 | `DROP DATABASE IF EXISTS bokyung`, `CREATE DATABASE bokyung` |
| 문자셋 | `utf8mb4`, `utf8mb4_unicode_ci` |
| 테이블 생성 순서 | Dept -> Professor -> Student -> Lecture -> Enrollment -> Grade |
| 재실행 안전성 | 자식 테이블부터 DROP 후 부모 테이블 DROP |

### 5.2 `jnu_public_seed.sql` 구현 설명

`jnu_public_seed.sql`은 공식 공개 학과 데이터를 `Dept`에 반영한다. 기존 기본 샘플 학과와 공식 공개 학과가
같은 이름이면 `ON DUPLICATE KEY UPDATE`로 단과대학, 사무실, 전화번호를 갱신한다.

| 컬럼 | 반영 방식 |
| --- | --- |
| dname | 공식 공개 학과명 |
| college | 공식 공개 단과대학명 |
| office | 실제 사무실 대신 101호~214호 숫자형 더미 호실 |
| tel | 공식 공개 전화번호 또는 대표 전화번호 |

공식 데이터 여부는 `office REGEXP '^[0-9]{3}호$'` 조건으로 구분한다. 이 조건을 사용하면 기본 샘플 학과와
공식 공개 학과 데이터를 분리하여 검증할 수 있다.

```sql
SELECT COUNT(*) AS official_public_dept_count
FROM Dept
WHERE office REGEXP '^[0-9]{3}호$';
```

## 6. 함수 종속성 및 정규화 과정

7주차 정규화 강의자료의 흐름에 따라 함수 종속성을 먼저 식별하고, 이상 현상을 유발하는 결정자를
분리하는 방식으로 정규화를 수행하였다. 함수 종속성은 `X -> Y`로 표현하며, X가 정해지면 Y가
유일하게 결정되는 관계를 의미한다. 정규화의 목적은 한 릴레이션에 여러 주제의 정보가 섞여 발생하는
삽입 이상, 삭제 이상, 갱신 이상을 줄이는 것이다.

### 6.1 초기 비정규 설계

초기에는 학생의 수강과 성적 조회를 쉽게 하기 위해 다음과 같은 하나의 평면 릴레이션을 가정하였다.

```text
CourseGradeRaw(
  stuid, sname, stu_year, phone, email,
  deptid, dname, college, office, tel,
  pid, pname, prof_rank,
  lid, lname, lnum, credit, semester,
  enroll_date, status, enroll_type,
  score, grade_letter, evaluation_date, remark
)
```

이 릴레이션은 학생 정보, 학과 정보, 교수 정보, 강의 정보, 수강신청 정보, 성적 정보가 한 행에 모두
섞여 있다. 학생 한 명이 여러 강의를 수강하면 학생 이름, 전화번호, 학과명이 반복되고, 같은 강의에
여러 학생이 수강하면 강의명, 학점, 담당 교수 정보가 반복된다.

### 6.2 초기 설계의 함수 종속성

| 결정자 | 종속 속성 | 의미 |
| --- | --- | --- |
| stuid | sname, stu_year, phone, email, deptid, advisor_pid | 학번이 학생 정보를 결정 |
| deptid | dname, college, office, tel | 학과번호가 학과 정보를 결정 |
| dname | deptid | 학과명은 UNIQUE이므로 학과번호를 결정 |
| pid | pname, prof_rank, email, office, deptid | 교번이 교수 정보를 결정 |
| lid | lname, lnum, credit, semester, pid | 강의번호가 강의 정보를 결정 |
| enrollid | stuid, lid, enroll_date, status, semester, enroll_type | 수강신청 ID가 수강신청 정보를 결정 |
| (stuid, lid, semester) | enrollid, enroll_date, status, enroll_type | 동일 학기 중복 신청을 방지하는 후보키 |
| gradeid | enrollid, score, grade_letter, evaluation_date, remark | 성적 ID가 성적 정보를 결정 |
| enrollid | gradeid, score, grade_letter, evaluation_date, remark | 수강신청 1건당 성적 1건 |

### 6.3 초기 설계의 이상 현상

| 이상 현상 | 발생 예시 |
| --- | --- |
| 삽입 이상 | 아직 수강신청이 없는 신설 학과나 신규 강의를 등록하기 어렵다. |
| 삭제 이상 | 학생의 마지막 수강행을 삭제하면 해당 학생의 소속 학과나 강의 정보까지 함께 사라질 수 있다. |
| 갱신 이상 | 학과 전화번호가 변경되면 해당 학과 학생의 모든 수강행을 수정해야 하며 일부만 수정하면 불일치가 발생한다. |

### 6.4 1NF 적용

제1정규형은 모든 속성 값이 원자값이어야 한다. 따라서 한 학생의 여러 강의를 한 셀에 저장하지 않고,
수강신청 1건을 하나의 행으로 표현하였다. 이 단계에서 반복 그룹을 제거하고 각 행이 하나의 수강신청
사건을 나타내도록 정리하였다.

### 6.5 2NF 적용

초기 수강 중심 릴레이션의 자연 후보키는 `(stuid, lid, semester)`로 볼 수 있다. 그러나 `sname`, `phone`,
`email`은 복합키 전체가 아니라 `stuid`에만 종속되고, `lname`, `credit`, `pid`는 `lid`에만 종속된다.
이는 부분 함수 종속이므로 제2정규형을 위반한다.

이를 제거하기 위해 다음과 같이 분해하였다.

| 분해 전 문제 | 분해 후 |
| --- | --- |
| stuid에만 종속되는 학생 정보 반복 | Student |
| lid에만 종속되는 강의 정보 반복 | Lecture |
| 수강신청 관계 자체의 속성 | Enrollment |

### 6.6 3NF 적용

제3정규형은 기본키가 아닌 속성이 기본키에 이행적으로 종속하지 않아야 한다. 예를 들어 Student 안에
학과명과 단과대학명을 같이 저장하면 `stuid -> deptid -> dname, college, tel` 이행 종속이 발생한다.
Lecture 안에 교수명을 같이 저장하면 `lid -> pid -> pname, prof_rank` 이행 종속이 발생한다.

이를 제거하기 위해 다음처럼 분리하였다.

| 이행 종속 | 분리 결과 |
| --- | --- |
| stuid -> deptid -> dname, college, tel | Dept를 별도 릴레이션으로 분리 |
| pid -> deptid -> dname, college | Professor는 deptid만 참조 |
| lid -> pid -> pname, prof_rank | Lecture는 pid만 참조하고 Professor 분리 |

### 6.7 M:N 관계 정규화

Student와 Lecture는 한 학생이 여러 강의를 수강하고, 한 강의에 여러 학생이 수강하는 M:N 관계이다.
관계형 모델에서는 M:N 관계를 직접 하나의 FK로 표현할 수 없으므로 `Enrollment`를 교차 릴레이션으로
도입하였다. `Enrollment`는 `stuid`, `lid`를 외래키로 가지고, 수강신청일, 수강 상태, 신청 구분처럼
수강 관계 자체에 속한 속성을 저장한다.

### 6.8 성적 정보 분리

성적은 학생이나 강의에 직접 종속되는 것이 아니라 수강신청 1건에 대해 부여되는 결과이다. 따라서
`Grade`를 별도 릴레이션으로 분리하고 `enrollid`를 FK로 두었다. 또한 `Grade.enrollid`에 UNIQUE 제약을
두어 수강신청 1건에 성적이 여러 번 저장되는 1:1 위반을 방지하였다.

### 6.9 BCNF 검증

BCNF는 모든 함수 종속성 `X -> Y`에서 결정자 X가 후보키여야 한다. 최종 릴레이션은 다음과 같이
주요 결정자가 모두 기본키 또는 후보키가 되도록 분리하였다.

| 릴레이션 | 후보키 | BCNF 판단 |
| --- | --- | --- |
| Student | stuid, email | stuid와 email이 학생 정보를 결정하므로 BCNF 만족 |
| Dept | deptid, dname | deptid와 dname이 학과 정보를 결정하므로 BCNF 만족 |
| Professor | pid, email | pid와 email이 교수 정보를 결정하므로 BCNF 만족 |
| Lecture | lid | lid가 강의 정보를 결정하므로 BCNF 만족 |
| Enrollment | enrollid, (stuid,lid,semester) | 두 후보키가 수강신청 정보를 결정하므로 BCNF 만족 |
| Grade | gradeid, enrollid | gradeid와 enrollid가 성적 정보를 결정하므로 BCNF 만족 |

### 6.10 무손실 분해 및 종속성 보존

정규화 과정에서 분해된 릴레이션들은 공통 속성이 한쪽 릴레이션의 키가 되도록 설계하였다. 예를 들어
Student와 Dept는 `deptid`를 공통 속성으로 가지며, `deptid`는 Dept의 기본키이다. 따라서 Student와 Dept를
조인하면 학생의 소속 학과 정보를 복원할 수 있다. Enrollment와 Grade도 `enrollid`를 공통 속성으로
가지며, `enrollid`는 Enrollment의 기본키이자 Grade의 UNIQUE 속성이므로 수강신청-성적 관계를 무손실로
복원할 수 있다.

### 8.3 Transaction

학사 DB에서는 수강신청, 성적 입력, 학과 정보 수정처럼 여러 작업이 하나의 업무 단위로 처리되어야 한다.
중간에 오류가 발생하면 일부 데이터만 반영되는 문제가 생기므로 Transaction을 사용하였다.

| Transaction 예제 | 사용 이유 | 검증 목적 | 실제 DB 사용 상황 |
| --- | --- | --- | --- |
| 수강신청 + 성적 입력 COMMIT | 여러 INSERT를 하나의 업무 단위로 처리 | 모두 성공할 때만 저장되는지 확인 | 성적 확정 처리 |
| 성적 점수 변경 후 ROLLBACK | 잘못된 변경을 취소 | 원래 값으로 복구되는지 확인 | 성적 정정 취소 |
| SAVEPOINT 부분 롤백 | 일부 변경만 취소 | 중간 저장점 이후 작업만 되돌리는지 확인 | 성적 검토 단계별 수정 |
| 공식 학과 전화번호 임시 변경 후 ROLLBACK | 공식 데이터 변경 안전성 검증 | 임시 변경이 원복되는지 확인 | 학과 정보 수정 작업 검증 |

## 12. 결론(Conclusion)

본 프로젝트는 전남대학교 학생 정보·성적관리 업무를 대상으로 요구분석, 개념 모델링, 논리 모델링,
정규화, SQL 구현, 고급 기능, 성능 최적화까지 수행하였다. 특히 전남대학교 공식 공개 학과 데이터
114건을 `Dept`에 반영하여 실제 학교 공개 정보와 연결된 DB로 고도화하였다.

또한 7주차 정규화 자료의 흐름에 따라 함수 종속성을 식별하고, 초기 비정규 릴레이션에서 1NF, 2NF,
3NF, BCNF 순서로 분해하여 삽입 이상, 삭제 이상, 갱신 이상을 제거하였다. 최종 스키마는 모든 주요
결정자가 후보키가 되도록 설계되어 BCNF를 만족한다.

고급 기능은 실제 학사관리 상황을 기준으로 구현하였다. View는 반복 JOIN을 줄이고, Stored Procedure는
자주 사용하는 성적·학과 조회를 재사용 가능하게 하며, Transaction은 학사 데이터 변경의 원자성을
검증하고, Index는 대용량 데이터 검색 성능을 개선한다. CSV 대용량 적재 실험을 통해 수만 건 규모의
데이터에서도 무결성과 검색 최적화가 동작함을 확인할 수 있도록 구성하였다.

결론적으로 본 DB는 단순한 수강·성적 예제 스키마가 아니라, 전남대학교 공식 공개 학과 데이터와
개인정보 없는 대용량 학사 더미 데이터를 함께 사용하여 실제 학사행정 DB에서 요구되는 무결성,
정규화, 조회 편의성, 대량 적재, 성능 최적화까지 검증한 설계 결과물이다.
