## 0. 30초 요약 (이것만 외워도 절반은 한다)

> "대학의 **수강신청과 성적관리**를 다루는 데이터베이스를 만들었습니다.
> 학생·학과·교수·강의 4개의 핵심 테이블과, 수강신청·성적 2개의 연결 테이블,
> 총 **6개 테이블**로 구성했고, 중복을 없애기 위해 **정규화(BCNF)** 를 적용했습니다.

> **5만 건 데이터로 인덱스를 켜기 전/후 속도를 비교**했더니 약 **247배** 빨라졌습니다."

## 1. 이 프로젝트가 뭘 하는 건가요? (가장 기본)

대학에서 매 학기 일어나는 일을 컴퓨터로 관리하는 것입니다.

- 학생이 **수강신청**을 한다 → 어떤 학생이 어떤 강의를 듣는지 기록
- 학기가 끝나면 **성적**이 나온다 → 그 수강 건에 점수/등급을 매김
- 학생은 **학과**에 소속되고, 교수도 학과에 소속되며 **강의**를 담당한다

이걸 엑셀 한 장에 다 적으면 같은 정보가 계속 반복되고 실수가 생깁니다.
그래서 **정보를 종류별로 표(테이블)에 나눠 담고, 표들을 서로 연결**한 것이 이 프로젝트입니다.

## 2. 6개의 테이블(개체) — 각각 뭘 저장하나

| 테이블 | 한 줄 설명 | 핵심 정보 |
| --- | --- | --- |
| **Student(학생)** | 학생 한 명의 정보 | 학번, 이름, 학년, 연락처, 이메일 |
| **Dept(학과)** | 학과 하나의 정보 | 학과번호, 학과명, 단과대학, 사무실, 전화 |
| **Professor(교수)** | 교수 한 명의 정보 | 교번, 이름, 직급, 이메일, 연구실 |
| **Lecture(강의)** | 개설된 강의 하나 | 강의번호, 강의명, 학수번호, 학점, 학기 |
| **Enrollment(수강신청)** | "누가 무슨 과목을 신청했다" | 학생+강의 연결, 신청일, 상태, 학기 |
| **Grade(성적)** | "그 수강 건의 점수" | 점수, 등급(A+~F), 평가일 |

> **왜 6개인가?** 채점 기준이 "개체 6개 이하, 각 개체 속성 3~5개"라서,
> 핵심만 골라 **딱 6개, 각 5개 속성**으로 맞췄습니다. (군더더기 없음 = 좋은 설계)

## 3. 강한 개체 vs 약한 개체 (자주 나오는 질문!)

### 쉬운 비유
- **강한 개체(Strong Entity)** = "혼자서도 존재 의미가 있는 것"
  → 학생, 학과, 교수, 강의. (학생은 수강신청을 안 해도 그냥 학생으로 존재함)
- **약한 개체(Weak Entity)** = "다른 게 있어야만 존재할 수 있는 것"
  → 수강신청, 성적.

### 왜 수강신청과 성적이 약한 개체인가?
- **수강신청**은 "학생"과 "강의"가 둘 다 있어야 생깁니다. 학생 없이, 강의 없이
  수강신청만 따로 존재할 수 없죠. → **존재 의존**
- **성적**은 "수강신청"이 있어야 생깁니다. 신청도 안 했는데 성적이 나올 순 없으니까요.

> 한 줄 답변: "수강신청과 성적은 다른 개체가 있어야만 존재할 수 있어서 약한 개체로 봤습니다."

## 4. 테이블을 어떻게 연결했나 (관계 & 외래키)

### 외래키(FK)란?
한 표에서 **다른 표의 한 줄을 가리키는 손가락**입니다.
예: Student 표의 `deptid` 칸은 "이 학생은 Dept 표의 몇 번 학과 소속"을 가리킵니다.

### 6가지 관계 (각각 일상어로)

| 관계 | 무슨 뜻 | 어떻게 연결했나 |
| --- | --- | --- |
| 학생 N : 1 학과 | 학생 여러 명이 한 학과에 속함 | Student.deptid → Dept |
| 교수 N : 1 학과 | 교수 여러 명이 한 학과에 속함 | Professor.deptid → Dept |
| 교수 1 : N 학생 | 한 교수가 여러 학생을 지도 | Student.advisor_pid → Professor |
| 교수 1 : N 강의 | 한 교수가 여러 강의를 맡음 | Lecture.pid → Professor |
| 학생 M : N 강의 | 학생도 여러 강의, 강의도 여러 학생 | **Enrollment 표로 연결** |
| 수강신청 1 : 1 성적 | 신청 한 건에 성적 한 개 | Grade.enrollid → Enrollment (UNIQUE) |

### "M:N은 왜 따로 표를 만들었나?" (단골 질문)
학생 1명이 강의 여러 개를 듣고, 강의 1개도 학생 여러 명이 듣습니다(다대다).
이건 표 두 개만으로는 깔끔하게 표현이 안 됩니다.
그래서 **중간에 'Enrollment(수강신청)' 표를 끼워 넣어** "학생-강의 한 쌍"을 한 줄로 기록합니다.
→ 다대다(M:N)가 **두 개의 일대다(1:N)** 로 풀립니다.

```
학생 ──(1:N)── 수강신청 ──(N:1)── 강의
```

## 5. 참여 제약 (전체 참여 vs 부분 참여) — 헷갈리는 부분

"이 표의 모든 줄이 반드시 관계에 참여해야 하나?"를 따지는 것입니다.

- **전체 참여(반드시)** = FK 칸을 비울 수 없음(NOT NULL)
  예) 모든 학생은 **반드시** 학과가 있어야 함 → `deptid`는 비울 수 없음
- **부분 참여(선택)** = FK 칸을 비울 수 있음(NULL 허용)
  예) 학생에게 **지도교수가 아직 없을 수도** 있음 → `advisor_pid`는 비워둘 수 있음

> 실제로 12번 학생 '배수지'는 지도교수가 없음(NULL)으로 넣어, 부분 참여를 보여줬습니다.

## 6. 정규화 — "왜 표를 나눴나?" (점수 핵심)

### 한 문장 정의
**정규화 = 같은 정보가 여러 군데 중복 저장되지 않도록 표를 잘 나누는 것.**

### 안 나누면 무슨 일이 생기나? (이상 현상 3종)
모든 걸 한 표에 몰아넣었다고 상상해 봅시다(학생+학과+강의+성적이 한 줄에).

1. **삽입 이상**: 아직 수강생이 없는 새 학과를 등록하고 싶은데, 학생 줄이 없으면 못 넣음.
2. **삭제 이상**: 어떤 학생의 마지막 줄을 지웠더니 그 학과 이름까지 같이 사라짐.
3. **갱신 이상**: 학과 이름이 바뀌면 그 학과 학생 수백 줄을 다 고쳐야 함(하나라도 빠지면 불일치).

### 그래서 어떻게 했나
정보를 "주인"별로 나눴습니다.
- 학과 정보는 → Dept 표에만
- 교수 정보는 → Professor 표에만
- 학생 정보는 → Student 표에만

이러면 학과 이름이 바뀌어도 **Dept 표 한 줄만 고치면 끝**입니다.

### 1NF → 2NF → 3NF → BCNF (단계 쉽게)
- **1NF**: 한 칸에 값 하나만 (예: 전화번호 칸에 번호 2개 넣지 않기) ✅
- **2NF**: 키의 일부에만 딸린 정보가 없게 ✅
- **3NF**: "키가 아닌 것이 키가 아닌 다른 것을 결정"하지 않게 (이행 종속 제거) ✅
- **BCNF**: 모든 결정자(무언가를 정하는 기준)가 후보키이도록 ✅ ← **우리는 여기까지 만족**

> 한 줄 답변: "모든 테이블을 BCNF까지 정규화해서 중복과 이상 현상을 없앴습니다.
> BCNF는 3NF보다 더 엄격한 단계라, 자동으로 3NF도 만족합니다."

## 7. 함수 종속성(FD)이 뭔가요?

"**A를 알면 B가 자동으로 정해진다**"는 관계를 화살표로 쓴 것입니다. `A → B`.

- 예: `stuid → sname` = "학번을 알면 그 학생 이름이 하나로 정해진다"
- 예: `deptid → dname` = "학과번호를 알면 학과명이 정해진다"

정규화는 결국 이 화살표들을 분석해서 "엉뚱하게 딸려 있는 정보"를 가려내 표를 나누는 작업입니다.

## 8. 고급 기능 4종 — 무엇이고 왜 넣었나

### (1) 뷰(View) — `StudentGradeView`
- **뭐냐**: 여러 표를 미리 조인해 둔 "가상의 성적표 화면". 진짜 표는 아니고 저장된 SELECT문.
- **왜**: 매번 학생+강의+성적을 조인하는 복잡한 쿼리를 안 쓰고
  `SELECT * FROM StudentGradeView` 한 줄로 성적표를 봄. (편함 + 재사용)

### (2) 저장 프로시저(Stored Procedure) — `GetStudentGrade(학번)`
- **뭐냐**: DB 안에 저장해 둔 "함수/프로그램". 학번을 넣으면 그 학생의 성적과 **평점(GPA)** 을 계산해 줌.
- **왜**: 복잡한 계산(등급 → 4.5만점 환산)을 매번 손으로 안 짜고 호출만 하면 됨.
- **호출**: `CALL GetStudentGrade(1);` → 홍길동 평점 4.00 나옴.

### (3) 트랜잭션(Transaction) — 전부 되거나 전부 안 되거나
- **뭐냐**: 여러 작업을 **하나의 묶음**으로 처리. 중간에 문제 생기면 **전부 취소(ROLLBACK)**.
- **왜**: "수강신청 + 성적입력"을 묶었을 때, 하나만 되고 하나는 실패하면 데이터가 깨짐.
  묶어서 처리하면 **둘 다 성공(COMMIT)하거나 둘 다 취소**되어 안전함.
- **실증**: 점수를 일부러 잘못 바꾼 뒤 `ROLLBACK` 했더니 원래 값(92점)으로 되돌아옴. ✅
- **SAVEPOINT**: 묶음 안에서 "중간 저장점"을 찍어 일부만 되돌리는 것도 보여줌.

### (4) 인덱스(Index) — 책 뒤의 "찾아보기"
- **뭐냐**: 특정 칸으로 빨리 찾도록 만든 색인. 책 뒤 '찾아보기(색인)'와 똑같은 원리.
- **왜**: 이름으로 학생을 찾을 때, 색인이 없으면 1만 명을 처음부터 다 훑음(느림).
  색인이 있으면 바로 그 페이지로 점프(빠름).
- `idx_student_name`(이름), `idx_lecture_name`(강의명)을 만들었음.

## 9. 성능 실험 — "247배"가 어디서 나온 숫자인가 (자랑 포인트)

### 실험 방법
1. **데이터를 대량 생성**: 학생 1만, 강의 1천, 수강 5만, 성적 5만 건.
2. 인덱스 **없는 상태**에서 "이름으로 학생 찾기"를 실행하고 속도/방식을 측정.
3. 인덱스를 **만든 뒤** 똑같은 검색을 다시 측정.
4. 두 결과를 비교.

### 결과 (실제 측정값)
| | 인덱스 전 | 인덱스 후 |
| --- | --- | --- |
| 검색 방식 | `ALL`(1만 명 전체 훑기) | `ref`(색인으로 바로 점프) |
| 살펴본 행 수 | 약 10,000줄 | **1줄** |
| 실행 시간 | 약 2.72ms | 약 0.011ms |

→ **약 247배 빨라짐.** "적절한 인덱스 하나가 검색 속도를 극적으로 바꾼다"는 걸 숫자로 증명.

### 용어 풀이 (질문 대비)
- **EXPLAIN**: "이 쿼리를 DB가 어떻게 처리할지" 미리 보여주는 명령. (실행계획)
- **type=ALL**: 풀 스캔(전부 훑기) = 느림. **type=ref**: 인덱스 사용 = 빠름.
- **EXPLAIN ANALYZE**: 실제로 돌려보고 걸린 시간까지 알려주는 버전.

## 10. 자주 받는 질문 & 모범 답변 (이게 핵심!)

**Q1. 이 프로젝트 한마디로 설명해 보세요.**
> "대학 수강신청·성적관리를 위한 데이터베이스로, 6개 테이블을 BCNF로 정규화하고
> 뷰·프로시저·트랜잭션·인덱스를 구현했으며, 5만 건 데이터로 인덱스 성능을 247배까지 개선했습니다."

**Q2. 왜 테이블을 6개로 나눴나요? 하나로 하면 안 되나요?**
> "하나로 합치면 같은 정보가 중복되어 삽입·삭제·갱신 이상이 생깁니다.
> 정규화로 정보를 주인별로 분리해 중복을 없앴습니다."

**Q3. 약한 개체가 뭐고 어떤 게 약한 개체인가요?**
> "다른 개체가 있어야만 존재할 수 있는 개체입니다. 수강신청은 학생·강의가, 성적은 수강신청이
> 있어야 존재하므로 약한 개체로 설계했습니다."

**Q4. M:N 관계는 어떻게 처리했나요?**
> "학생과 강의는 다대다 관계라 직접 표현이 안 됩니다. 중간에 Enrollment 표를 둬서
> 1:N과 N:1 두 개로 분해했습니다."

**Q5. 외래키에 ON DELETE CASCADE를 왜 걸었나요?**
> "학생이나 강의가 삭제되면 그에 딸린 수강신청·성적도 자동으로 같이 지워져야 데이터가
> 깨지지 않기 때문입니다. 반대로 학과·교수는 RESTRICT로 막아 함부로 못 지우게 했습니다."

**Q6. 정규화 몇 차까지 했나요? 3NF와 BCNF 차이는?**
> "BCNF까지 했습니다. 3NF는 '이행 종속 제거', BCNF는 '모든 결정자가 후보키'로 더 엄격합니다.
> 6개 테이블 모두 결정자가 후보키여서 BCNF를 만족합니다."

**Q7. 인덱스를 모든 칸에 다 걸면 더 좋지 않나요?**
> "아닙니다. 인덱스는 조회는 빠르게 하지만, 데이터를 넣고 고칠 때는 색인도 같이 갱신해야 해서
> 쓰기가 느려지고 저장 공간도 더 씁니다. 그래서 자주 검색하는 칸(이름 등)에만 선택적으로 걸었습니다."

**Q8. 트랜잭션은 왜 필요한가요?**
> "여러 작업이 '모두 성공 아니면 모두 취소'가 되어야 데이터가 일관됩니다.
> 중간에 실패하면 ROLLBACK으로 깔끔하게 되돌릴 수 있습니다."

**Q9. 성적 등급(A+)을 점수에서 자동 계산하면 되는데 왜 따로 저장했나요?**
> "보통은 점수→등급이 자동이지만, 재수강 상한이나 정정 같은 예외가 있을 수 있어
> 등급을 독립적으로 저장해 유연성을 뒀습니다."

**Q10. 데이터가 잘못 들어가는 걸 어떻게 막나요?**
> "FK로 없는 학과·강의를 못 가리키게, CHECK로 점수(0~100)·학년(1~4) 범위를,
> UNIQUE로 같은 학기 중복 신청을 막습니다. 실제로 잘못된 값 입력 시 오류로 거부되는 걸 확인했습니다."

**Q11. RANK, YEAR 같은 이름을 왜 안 썼나요?**
> "MySQL 예약어와 충돌해서요. `rank`→`prof_rank`, `year`→`stu_year`로 바꿔 오류를 피했습니다."

**Q12. 실제로 실행은 해봤나요?**
> "네, MySQL 8.0.45에서 두 스크립트를 끝까지 오류 없이 실행했고, 5만 건 데이터·트랜잭션·
> 인덱스 성능까지 실측으로 확인했습니다."

## 13. 절대 틀리면 안 되는 핵심 숫자/사실

- 개체(테이블) **6개**, 각 **5개 속성** (강한 4 + 약한 2)
- 정규화 **BCNF** (3NF 포함)
- 외래키 **7개**
- 고급기능 **4종**: 뷰 / 프로시저 / 트랜잭션 / 인덱스
- 대용량: 학생 1만, 강의 1천, 수강 5만, 성적 5만
- 성능 개선: **약 247배** (2.72ms → 0.011ms), 검색방식 **ALL → ref**
- DBMS: **MySQL 8.0** (InnoDB, utf8mb4)
