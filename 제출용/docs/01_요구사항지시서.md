# 01. 요구사항지시서 (Requirements Specification)

**프로젝트명:** 전남대학교 수강신청·성적관리 데이터베이스 설계
**과목:** 데이터베이스 시스템 (Database Systems) 기말 프로젝트
**작성일:** 2026-05-31
**DBMS:** MySQL 8.0 (MySQL Workbench 기준)

---

## 1. 프로젝트 개요 및 목적

### 1.1 배경
대학의 학사 운영에서 가장 핵심이 되는 업무는 **학생의 수강신청**과 **성적 관리**이다.
학생은 매 학기 개설된 강의를 신청하고, 교수는 강의를 담당하며, 학기 종료 시 수강한 강의에 대한 성적이 부여된다.
이러한 업무는 학과(Dept), 교수(Professor), 학생(Student), 강의(Lecture) 등 여러 개체가 복잡한 관계로 얽혀 있어,
체계적인 데이터 모델링 없이 파일 기반으로 관리하면 **데이터 중복**, **갱신 이상(update anomaly)**,
**참조 무결성 훼손** 등의 문제가 발생한다.

### 1.2 목적
본 프로젝트의 목적은 다음과 같다.

1. 대학 수강신청·성적관리 업무를 **개념적 모델링(ER 모델)** 으로 분석한다.
2. 이를 **논리적 모델(관계 스키마)** 로 변환하고 **정규화(최대 BCNF)** 를 적용하여 이상 현상을 제거한다.
3. **MySQL DDL/DML**로 실제 데이터베이스를 구현하고 **참조 무결성**을 보장한다.
4. **뷰(View), 저장 프로시저(Stored Procedure), 트랜잭션(Transaction), 인덱스(Index)** 등
   고급 데이터베이스 기능을 적용한다.
5. **대용량 테스트 데이터(수만 건)** 를 생성하여 **인덱스 적용 전후 성능을 정량적으로 비교**하고
   질의 최적화의 효과를 실증한다.

### 1.3 시스템 범위
- 학과/교수/학생 기본 정보 관리
- 학기별 강의 개설 및 담당 교수 배정
- 학생의 수강신청 및 수강 상태(수강중/취소/완료) 관리
- 수강 건별 성적(점수·등급) 부여 및 조회
- 학생별 성적/평점 조회, 강의별 수강생 조회 등 통계성 질의

> 본 프로젝트는 데이터 모델링과 질의 최적화에 초점을 둔다. 인증/결제/시간표 충돌 검사 등
> 응용 계층의 기능은 범위에서 제외하되, 데이터 모델은 이러한 확장을 수용할 수 있도록 설계한다.

## 2. 개체(Entity) 식별 및 설명

업무 분석을 통해 총 **6개의 개체**를 식별하였다. 이 중 4개는 강 개체(Strong Entity),
2개는 약 개체(Weak Entity)이다.

### 2.1 강 개체 (Strong Entity)

강 개체는 자신의 키 속성만으로 인스턴스를 유일하게 식별할 수 있으며, 다른 개체의 존재에
의존하지 않는 개체이다.

| 번호 | 개체 | 한글명 | 설명 |
| --- | --- | --- | --- |
| 1 | **Student** | 학생 | 대학에 소속된 학생. 학번으로 유일하게 식별된다. |
| 2 | **Dept** | 학과 | 학생과 교수가 소속되는 학과. 학과번호로 식별된다. |
| 3 | **Professor** | 교수 | 강의를 담당하고 학생을 지도하는 교수. 교번으로 식별된다. |
| 4 | **Lecture** | 강의 | 학기마다 개설되는 강의(과목·분반). 강의번호로 식별된다. |

#### (1) Student (학생)
| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **stuid** | 학번 | 기본키(PK) |
| sname | 이름 | |
| stu_year | 학년 | 1~4 (`year`는 MySQL 예약어라 `stu_year` 사용) |
| phone | 연락처 | |
| email | 이메일 | |
| (deptid) | 소속 학과 | 외래키(FK) → Dept |
| (advisor_pid) | 지도교수 | 외래키(FK) → Professor |

#### (2) Dept (학과)
| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **deptid** | 학과번호 | 기본키(PK) |
| dname | 학과명 | |
| college | 단과대학 | |
| office | 학과 사무실 | |
| tel | 학과 전화 | |

#### (3) Professor (교수)
| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **pid** | 교번 | 기본키(PK) |
| pname | 이름 | |
| prof_rank | 직급 | 전임강사/조교수/부교수/정교수 (`rank`는 예약어라 `prof_rank` 사용) |
| email | 이메일 | |
| office | 연구실 | |
| (deptid) | 소속 학과 | 외래키(FK) → Dept |

#### (4) Lecture (강의)
| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **lid** | 강의번호 | 기본키(PK) |
| lname | 강의명 | |

| (pid) | 담당 교수 | 외래키(FK) → Professor |

### 2.2 약 개체 (Weak Entity)

약 개체는 **자신의 속성만으로는 인스턴스를 식별할 수 없고**, 소유 개체(owner)의 키에
의존하여 식별되는 개체이다. 본 설계에서는 다대다 관계와 평가 정보를 표현하기 위해
두 개의 약 개체를 도입하였다.

#### (5) Enrollment (수강신청)
학생(Student)과 강의(Lecture)의 **다대다(M:N) 관계를 해소**하기 위한 약 개체이다.
하나의 수강신청은 반드시 특정 학생과 특정 강의가 존재해야만 성립하므로, 두 강 개체에
**존재 의존(existence dependent)** 한다.

| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **enrollid** | 수강신청 ID | 기본키(PK, 대리키) |
| (stuid) | 신청 학생 | 외래키(FK) → Student (식별 관계) |
| (lid) | 신청 강의 | 외래키(FK) → Lecture (식별 관계) |
| enroll_date | 신청일 | |
| status | 수강 상태 | 수강중/취소/완료 |
| semester | 수강 학기 | |
| enroll_type | 신청 구분 | 정규/재수강 |

- **부분 키(partial key):** (stuid, lid, semester) 조합. 한 학생이 같은 학기에 같은 강의를
  중복 신청할 수 없도록 **UNIQUE 제약**으로 강제한다.

#### (6) Grade (성적)
수강신청(Enrollment) 한 건에 대한 평가 결과를 표현하는 약 개체이다.
성적은 반드시 특정 수강신청이 존재해야만 부여될 수 있으므로 Enrollment에 **존재 의존**한다.

| 속성 | 의미 | 비고 |
| --- | --- | --- |
| **gradeid** | 성적 ID | 기본키(PK, 대리키) |
| (enrollid) | 대상 수강신청 | 외래키(FK) → Enrollment (식별 관계, UNIQUE) |
| score | 점수 | 0~100 |
| grade_letter | 등급 | A+, A0, B+, ... , F |
| evaluation_date | 평가일 | |
| remark | 비고 | 재수강/이의신청 등 메모 |

> **설계 메모:** 구현 단계에서는 SQL 작성을 단순화하기 위해 약 개체에도 **대리키(surrogate key)**
> `enrollid`, `gradeid`를 부여한다. 다만 약 개체의 본질(존재 의존, 식별 관계)은
> FK NOT NULL 제약과 UNIQUE 제약으로 그대로 보존한다.

### 2.3 개체별 고유 속성 수 (속성 개수 제약 충족)

각 개체는 **고유 속성 5개**로 구성된다(관계에서 파생되는 외래키는 개념 모델 상 개체의 고유
속성이 아니라 관계 매핑의 산물이므로 별도 표기). 모든 개체가 **3개 이상 5개 이하** 속성 조건을
만족하며, 개체 수는 **6개**이다.

| 개체 | 고유 속성(키 포함) | 고유 속성 수 | 관계 파생 FK |
| --- | --- | --- | --- |
| Student | stuid, sname, stu_year, phone, email | 5 | deptid, advisor_pid |
| Dept | deptid, dname, college, office, tel | 5 | — |
| Professor | pid, pname, prof_rank, email, office | 5 | deptid |
| Lecture | lid, lname, lnum, credit, semester | 5 | pid |
| Enrollment | enrollid, enroll_date, status, semester, enroll_type | 5 | stuid, lid |
| Grade | gradeid, score, grade_letter, evaluation_date, remark | 5 | enrollid |

## 3. 관계(Relationship) 및 카디널리티

식별된 6개 개체 사이의 관계와 카디널리티(cardinality)는 다음과 같다.

| 번호 | 관계명 | 관계 | 관계 의미 | 카디널리티 | 구현 방식 |
| --- | --- | --- | --- | --- | --- |
| R1 | belong(소속) | Student — Dept | 학생은 한 학과에 소속된다 | **N : 1** | Student.deptid FK |
| R2 | work_dept(근무) | Professor — Dept | 교수는 한 학과에서 근무한다 | **N : 1** | Professor.deptid FK |
| R3 | tutor(지도) | Professor — Student | 교수는 여러 학생을 지도한다 | **1 : N** | Student.advisor_pid FK |
| R4 | manage(담당) | Professor — Lecture | 교수는 여러 강의를 담당한다 | **1 : N** | Lecture.pid FK |
| R5 | study(수강) | Student — Lecture | 학생은 여러 강의를 수강한다 | **M : N** | Enrollment 교차 개체 |
| R6 | evaluate(평가) | Enrollment — Grade | 수강신청 1건당 성적 1건 | **1 : 1** | Grade.enrollid FK + UNIQUE |

> 각 관계는 교수님 요구사항 양식(belong/study/tutor/manage/work-dept)에 맞춘 **관계명**을 부여하였다.
> 카디널리티(관계대응수)와 함께 **최소 참여(최소값)** 는 §4 참여 제약에서 상세히 규정한다.

### 3.1 다대다(M:N) 관계의 해소
R5 (Student M:N Lecture)는 관계형 모델에서 직접 표현할 수 없으므로,
**교차 개체(associative entity)** 인 **Enrollment**를 도입하여
`Student 1:N Enrollment N:1 Lecture` 형태의 두 개의 일대다 관계로 분해한다.

```
Student (1) ──< Enrollment >── (1) Lecture
              N            N
```

### 3.2 일대일(1:1) 관계
R6 (Enrollment 1:1 Grade)는 Grade 테이블의 `enrollid`에 **UNIQUE 제약**을 부여하여
하나의 수강신청에 최대 하나의 성적만 연결되도록 보장한다.

## 4. 참여 제약 (Participation Constraints)

참여 제약은 한 개체의 모든 인스턴스가 관계에 반드시 참여해야 하는지(전체 참여, total)
또는 선택적으로 참여하는지(부분 참여, partial)를 규정한다.
(ER 다이어그램에서 전체 참여는 이중선, 부분 참여는 단일선으로 표기한다.)

| 관계 | 개체 | 참여 유형 | 근거 |
| --- | --- | --- | --- |
| R1 Student–Dept | Student | **전체 참여(total)** | 모든 학생은 반드시 소속 학과가 있다 → `deptid NOT NULL` |
| R1 Student–Dept | Dept | 부분 참여(partial) | 학생이 한 명도 없는 학과가 존재할 수 있다 |
| R2 Professor–Dept | Professor | **전체 참여(total)** | 모든 교수는 반드시 소속 학과가 있다 → `deptid NOT NULL` |
| R2 Professor–Dept | Dept | 부분 참여(partial) | 교수가 없는 신설 학과가 존재할 수 있다 |
| R3 Professor–Student | Student | 부분 참여(partial) | 지도교수 미배정 학생이 있을 수 있다 → `advisor_pid NULL 허용` |
| R3 Professor–Student | Professor | 부분 참여(partial) | 지도 학생이 없는 교수가 있을 수 있다 |
| R4 Professor–Lecture | Lecture | **전체 참여(total)** | 모든 강의는 담당 교수가 있어야 한다 → `pid NOT NULL` |
| R4 Professor–Lecture | Professor | 부분 참여(partial) | 강의를 맡지 않는 교수가 있을 수 있다 |
| R5 Enrollment 양측 | Enrollment | **전체 참여(total)** | 수강신청은 학생·강의가 모두 존재해야 성립 → 두 FK 모두 NOT NULL |
| R6 Enrollment–Grade | Grade | **전체 참여(total)** | 성적은 반드시 수강신청에 종속 → `enrollid NOT NULL` |
| R6 Enrollment–Grade | Enrollment | 부분 참여(partial) | 아직 성적이 부여되지 않은 수강신청이 있을 수 있다 |

## 5. 업무 규칙 (Business Rules)

데이터 무결성을 위해 다음 업무 규칙을 정의하고, 이후 단계에서 제약조건으로 구현한다.

- **BR1.** 학번(stuid), 교번(pid), 학과번호(deptid), 강의번호(lid)는 각각 유일하다. *(PK)*
- **BR2.** 학생과 교수의 소속 학과는 반드시 존재하는 학과여야 한다. *(FK, NOT NULL)*
- **BR3.** 강의의 담당 교수는 반드시 존재하는 교수여야 한다. *(FK, NOT NULL)*
- **BR4.** 한 학생은 같은 학기에 같은 강의를 중복 신청할 수 없다. *(UNIQUE(stuid, lid, semester))*
- **BR5.** 수강신청 상태는 '수강중', '취소', '완료' 중 하나여야 한다. *(CHECK/ENUM)*
- **BR6.** 신청 구분은 '정규', '재수강' 중 하나여야 한다. *(CHECK/ENUM)*
- **BR7.** 성적 점수는 0 이상 100 이하여야 한다. *(CHECK)*
- **BR8.** 하나의 수강신청에는 최대 하나의 성적만 존재한다. *(UNIQUE(enrollid))*
- **BR9.** 학생/강의가 삭제되면 해당 수강신청과 성적도 함께 삭제된다. *(ON DELETE CASCADE)*
- **BR10.** 강의 학점(credit)은 1~3 사이의 값이다. *(CHECK)*
