## 2. 개념적 모델링 (Conceptual Modeling)

### 2.1 개체 추출
업무 분석 결과 다음 6개 개체를 도출하였다.

- **강 개체(4):** Student(학생), Dept(학과), Professor(교수), Lecture(강의)
- **약 개체(2):** Enrollment(수강신청), Grade(성적)

### 2.2 개념 ER 모델 요약
- Student는 Dept에 **N:1**, Professor는 Dept에 **N:1** 로 소속된다.
- Professor는 Student를 **1:N**(지도), Lecture를 **1:N**(담당) 관계로 가진다.
- Student와 Lecture는 본질적으로 **M:N** 관계이며, 이를 교차 개체 **Enrollment**로 해소한다.
- Enrollment와 Grade는 **1:1** 관계이다.

자세한 다이어그램은 `erd_description.md` 참조.

### 2.3 약 개체 식별
- **Enrollment**는 Student와 Lecture가 존재해야만 성립하는 존재 의존 개체이며,
  부분 키는 (stuid, lid, semester)이다.
- **Grade**는 Enrollment가 존재해야만 성립하는 존재 의존 개체이며, Enrollment에 1:1로 대응한다.

### 2.4 각 개체의 기본키 및 속성별 중복 가능 여부

각 개체의 기본키(PK)를 명시하고, 모든 속성에 대해 값의 **중복 가능 여부**를 분석한다.

## 3. 논리적 모델링 (Logical Modeling)

개념 모델을 관계 스키마로 변환한 결과는 다음과 같다(밑줄=PK, * =FK).

```
Dept(deptid, dname, college, office, tel)
Professor(pid, pname, prof_rank, email, office, *deptid)
Student(stuid, sname, stu_year, phone, email, *deptid, *advisor_pid)
Lecture(lid, lname, lnum, credit, semester, *pid)
Enrollment(enrollid, *stuid, *lid, enroll_date, status, semester, enroll_type)
Grade(gradeid, *enrollid, score, grade_letter, evaluation_date, remark)
```

변환 규칙:
1. 강 개체 → 독립 테이블
2. N:1 관계 → 다(N) 쪽에 FK 부여
3. M:N 관계 → 교차 테이블(Enrollment) 생성
4. 1:1 관계 → FK + UNIQUE(Grade.enrollid)
5. 약 개체 → 소유 개체 키를 NOT NULL FK로 포함

#### 관계별 외래키(FK) 삽입 설명
- **R1 belong (Student N:1 Dept):** `Student.deptid(FK)` → `Dept(deptid)` 참조.
  N:1 관계라 N쪽(Student)에 FK를 추가하여 학생의 소속 학과를 표현.
- **R2 work_dept (Professor N:1 Dept):** `Professor.deptid(FK)` → `Dept(deptid)` 참조. 교수 소속 학과 표현.
- **R3 tutor (Professor 1:N Student):** `Student.advisor_pid(FK)` → `Professor(pid)` 참조.
  N쪽(Student)에 FK 추가. 미배정 허용을 위해 NULL 가능.
- **R4 manage (Professor 1:N Lecture):** `Lecture.pid(FK)` → `Professor(pid)` 참조. 강의 담당 교수 표현.
- **R5 study (Student M:N Lecture):** 다대다라 교차 테이블 `Enrollment` 생성,
  `Enrollment.stuid(FK)`→Student, `Enrollment.lid(FK)`→Lecture 두 FK로 분해.
- **R6 evaluate (Enrollment 1:1 Grade):** `Grade.enrollid(FK)` → `Enrollment(enrollid)` 참조 + UNIQUE로 1:1 보장.

## 4. 함수 종속성 분석 (Functional Dependency Analysis)

각 릴레이션의 함수 종속성(FD)을 분석한다. (X → Y : X가 Y를 결정)

### 4.1 Dept
```
deptid → dname, college, office, tel
dname  → deptid          (학과명도 유일하므로 후보키)
```
- 후보키: {deptid}, {dname} / 기본키: deptid
- 모든 비키 속성이 후보키에 **완전 함수 종속**이며, 이행 종속 없음.

### 4.2 Professor
```
pid → pname, prof_rank, email, office, deptid
email → pid              (email UNIQUE → 후보키)
```
- 후보키: {pid}, {email} / 기본키: pid
- 결정자가 모두 후보키 → 이상 현상 없음.

### 4.3 Student
```
stuid → sname, stu_year, phone, email, deptid, advisor_pid
email → stuid            (email UNIQUE → 후보키)
```
- 후보키: {stuid}, {email} / 기본키: stuid
- `deptid`, `advisor_pid`는 stuid에만 종속(부분/이행 종속 없음).

### 4.4 Lecture
```
lid → lname, lnum, credit, semester, pid
```
- 후보키: {lid} / 기본키: lid
- 단일 결정자, 이상 없음.

### 4.5 Enrollment
```
enrollid → stuid, lid, enroll_date, status, semester, enroll_type
(stuid, lid, semester) → enrollid     (UNIQUE → 후보키)
```
- 후보키: {enrollid}, {stuid, lid, semester} / 기본키: enrollid
- 모든 결정자가 후보키. `status`, `enroll_type` 등은 enrollid에 완전 종속.

### 4.6 Grade
```
gradeid  → enrollid, score, grade_letter, evaluation_date, remark
enrollid → gradeid                    (UNIQUE → 후보키)
```
- 후보키: {gradeid}, {enrollid} / 기본키: gradeid
- score → grade_letter 의 도메인 규칙이 존재할 수 있으나(점수→등급), 이는 응용 규칙으로 처리하며
  성적 정정·가중치 변경 가능성을 고려하여 grade_letter를 독립 저장한다(설계 선택).

## 5. 정규화 (Normalization)

### 5.1 정규화 목표
삽입·삭제·갱신 이상(anomaly)을 제거하고 데이터 중복을 최소화하기 위해 **BCNF**까지 정규화한다.

### 5.2 단계별 검증

| 정규형 | 조건 | 본 스키마 만족 여부 |
| --- | --- | --- |
| **1NF** | 모든 속성이 원자값 | ✔ 다치/복합 속성 없음. 모든 컬럼 원자값 |
| **2NF** | 1NF + 부분 함수 종속 제거 | ✔ 복합키 후보(Enrollment)에서도 비키 속성이 전체키에 완전 종속 |
| **3NF** | 2NF + 이행 함수 종속 제거 | ✔ 비키→비키 종속 없음(예: college가 deptid를 거치지 않고 직접 결정되는 구조 아님) |
| **BCNF** | 모든 결정자가 후보키 | ✔ 4장의 FD 분석에서 모든 결정자가 후보키임을 확인 |

### 5.3 정규화 사례 분석 (비정규 → 정규)

**(가) 정규화 이전(가상의 평면 테이블)**
수강 정보를 하나의 테이블에 몰아넣으면 다음과 같은 비정규 구조가 된다.

```
BigEnroll(stuid, sname, deptid, dname, college,
          lid, lname, pid, pname, score, grade_letter, semester)
```

이 테이블의 함수 종속:
```
stuid  → sname, deptid
deptid → dname, college        ← 이행 종속! (stuid → deptid → dname)
lid    → lname, pid
pid    → pname                 ← 이행 종속! (lid → pid → pname)
```

**(나) 발생하는 이상 현상**
- **삽입 이상:** 아직 수강생이 없는 신설 학과/강의를 등록할 수 없다.
- **삭제 이상:** 마지막 수강 행을 지우면 학과명·강의명 정보까지 사라진다.
- **갱신 이상:** 학과명이 바뀌면 해당 학과 학생의 모든 행을 갱신해야 한다(불일치 위험).

**(다) 정규화 결과**
이행 종속을 제거하기 위해 결정자별로 테이블을 분해하였다.

```
Student(stuid, sname, ..., deptid)        ← stuid → sname, deptid
Dept(deptid, dname, college, ...)          ← deptid → dname, college  (이행종속 분리)
Lecture(lid, lname, ..., pid)              ← lid → lname, pid
Professor(pid, pname, ...)                 ← pid → pname             (이행종속 분리)
Enrollment(enrollid, stuid, lid, semester) ← M:N 해소
Grade(gradeid, enrollid, score, ...)       ← 평가 정보 분리
```

→ 분해 후 모든 테이블에서 **이행 종속이 제거**되고, 각 사실(fact)이 한 곳에만 저장되어
세 가지 이상 현상이 모두 해소되었다. 또한 분해는 **무손실 조인(lossless join)** 과
**함수 종속 보존(dependency preserving)** 을 만족한다(공유 속성 deptid, pid, enrollid가
각각 분해된 테이블의 후보키이므로).

```sql
  enrollid    INT AUTO_INCREMENT PRIMARY KEY,
  stuid       INT NOT NULL,
  lid         INT NOT NULL,

      ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT uq_enroll UNIQUE (stuid, lid, semester)
) ENGINE=InnoDB;
```

## 7. 고급 기능 구현

`sql/optimization.sql`에 구현하였다.

### 7.1 뷰 (View) — `StudentGradeView`
학생·강의·성적을 조인하여 성적표 형태로 제공하는 뷰.
```sql
CREATE OR REPLACE VIEW StudentGradeView AS
SELECT s.stuid, s.sname, d.dname,
       l.lname, l.credit, e.semester,
       g.score, g.grade_letter
FROM Student s
JOIN Dept d        ON s.deptid = d.deptid
JOIN Enrollment e  ON e.stuid  = s.stuid
JOIN Lecture l     ON e.lid    = l.lid
LEFT JOIN Grade g  ON g.enrollid = e.enrollid;
```

### 7.2 저장 프로시저 (Stored Procedure) — `GetStudentGrade()`
특정 학생의 성적과 평점 평균(GPA 근사)을 반환.
```sql
CALL GetStudentGrade(1);
```

### 7.3 트랜잭션 (Transaction)
수강신청과 성적 입력을 원자적으로 처리하는 예제. 오류 시 `ROLLBACK`, 정상 시 `COMMIT`.
`SAVEPOINT`를 이용한 부분 롤백 예제 포함.

### 7.4 인덱스 (Index)
`idx_student_name`, `idx_lecture_name`, `idx_enroll_stu`, `idx_enroll_lec` 등 생성.

| Grade | 50,000 |

### 8.3 실험 절차
1. 인덱스가 없는 상태에서 대상 질의 3종을 `EXPLAIN`으로 분석하고 실행 시간을 측정한다.
2. 인덱스를 생성한다.
3. 동일 질의를 다시 `EXPLAIN`·측정하여 비교한다.

### 8.4 대상 질의 (optimization.sql PART 5와 동일)
- **Q1.** 이름으로 학생 검색: `SELECT * FROM Student WHERE sname = '학생05000';`
  → 인덱스 `idx_student_name`
- **Q2.** 강의명으로 강의 검색: `SELECT * FROM Lecture WHERE lname = '강의0777';`
  → 인덱스 `idx_lecture_name`
- **Q3.** 이름으로 학생을 찾아 수강내역과 조인:
  `SELECT COUNT(*) FROM Student s JOIN Enrollment e ON e.stuid=s.stuid WHERE s.sname='학생05000';`
  → 구동 테이블(Student)에 `idx_student_name` 적용

> **인덱스 선정 근거:** InnoDB는 외래키 컬럼(`Enrollment.stuid`, `Enrollment.lid`)에 대해
> **자동으로 보조 인덱스를 생성**한다. 따라서 전/후 비교가 의미 있으려면 자동 인덱스가 없는
> 컬럼을 대상으로 해야 하며, 본 실험은 비(非)키·비(非)FK 컬럼인 `sname`·`lname`을 선택하였다.
> Q3는 조인 질의에서 **구동 테이블의 인덱스 유무**가 전체 비용에 미치는 영향을 보이기 위한 것이다.

### 8.5 실험 결과 (MySQL 8.0.45 실측값)

> 아래 수치는 본 프로젝트의 `schema.sql`→`optimization.sql`을 **MySQL 8.0.45에서 실제 실행**하여
> `EXPLAIN` 및 `EXPLAIN ANALYZE`로 측정한 값이다(데이터: 학생 10,012 / 강의 1,008 /
> 수강 50,019 / 성적 50,014건). 절대 실행시간은 하드웨어·캐시 상태에 따라 달라질 수 있다.

**Q1. `SELECT * FROM Student WHERE sname = '학생05000';` (EXPLAIN ANALYZE 실측)**

| 항목 | 인덱스 적용 전 | 인덱스 적용 후 | 개선 |
| --- | --- | --- | --- |
| EXPLAIN type | ALL (풀스캔) | ref | 스캔 → 인덱스 탐색 |
| 추정 비용(cost) | 994 | 0.35 | **약 2,840배↓** |
| 실제 검사 행(actual rows) | 10,012 | 1 | 약 1만배↓ |
| 실제 실행시간 | 약 2.72 ms | 약 0.011 ms | **약 247배↑** |

**Q2·Q3 (EXPLAIN 실측 요약)**

| 질의 | 항목 | 인덱스 적용 전 | 인덱스 적용 후 |
| --- | --- | --- | --- |
| Q2 (lname 검색) | type / rows | ALL / 1,008 | ref / 1 (idx_lecture_name) |
| Q3 (이름 조인, 구동 테이블) | type / rows | ALL / 9,858 | ref / 1 (idx_student_name) |

→ 세 질의 모두 인덱스 적용 후 `type`이 **ALL → ref**로 전환되고, 검사 행 수가
**수천~수만 분의 1**로 감소하였다. 특히 Q1의 `EXPLAIN ANALYZE` 실측에서 실행시간이
**약 2.72ms → 0.011ms(약 247배 단축)**, 추정 비용은 **994 → 0.35**로 급감하였다.

### 8.6 분석
- 인덱스 적용 전에는 `type=ALL`(전체 테이블 스캔)으로, 검사 행 수가 테이블 전체에 비례한다.
- 인덱스 적용 후 `type=ref`로 전환되어 **B+Tree 인덱스 탐색**으로 필요한 행만 접근한다.
- 조인 질의(Q3)에서도 구동 테이블 인덱스로 시작 행이 1건으로 좁혀져, 이후 FK 인덱스를 통한
  조인 비용까지 함께 절감된다.
- 다만 인덱스는 **쓰기 비용 증가**와 **저장 공간**이라는 트레이드오프가 있으므로,
  조회 빈도가 높은 컬럼(이름 등)에 선택적으로 부여하였다.

### 8.7 결론
적절한 인덱스 설계만으로 핵심 질의에서 **두 자릿수~세 자릿수 배(실측 최대 약 247배)의
응답 시간 개선**을 확인하였다. 최적화된 데이터베이스가 비최적화 대비 유의미하게 우수함을
실측으로 실증하였다.

본 프로젝트는 대학 수강신청·성적관리 업무를 대상으로 **개념 → 논리 → 물리** 설계를 일관되게
수행하고, 모든 릴레이션을 **BCNF**로 정규화하여 데이터 이상 현상을 제거하였다.
또한 뷰·저장 프로시저·트랜잭션·인덱스 등 고급 기능을 구현하고,
**5만 건 규모의 대용량 데이터 기반 인덱스 전후 성능 실험**으로 질의 최적화의 효과를
정량적으로 입증하였다. 설계의 모든 단계가 무결성 제약으로 보호되어 신뢰성 있는
데이터베이스를 완성하였다.
