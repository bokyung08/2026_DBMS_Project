## 1. 개념적 모델링 (세부 내용)

[요소1] 각 개체의 기본키 명시 + 모든 속성의 중복 가능 여부 서술

■ 학생(Student) — 기본키: stuid
- stuid : 기본키, 중복 불가(학번은 학생마다 유일)
- sname : 중복 가능(동명이인 존재 가능)
- stu_year : 중복 가능(같은 학년 학생 다수)
- phone : 중복 가능
- email : UNIQUE, 중복 불가(이메일은 유일)

■ 학과(Dept) — 기본키: deptid
- deptid : 기본키, 중복 불가(유일)
- dname : UNIQUE, 중복 불가(학과명 유일)
- college : 중복 가능(여러 학과가 같은 단과대학)
- office : 중복 가능
- tel : 중복 가능

■ 교수(Professor) — 기본키: pid
- pid : 기본키, 중복 불가(유일)
- pname : 중복 가능(동명이인 가능)
- prof_rank : 중복 가능(같은 직급 다수)
- email : UNIQUE, 중복 불가(유일)
- office : 중복 가능

■ 강의(Lecture) — 기본키: lid
- lid : 기본키, 중복 불가(유일)
- lname : 중복 가능(같은 과목 여러 분반)
- lnum : 중복 가능(실무상 유일 경향)
- credit : 중복 가능(같은 학점 다수)
- semester : 중복 가능(같은 학기 다수)

■ 수강신청(Enrollment) — 기본키: enrollid
- enrollid : 기본키, 중복 불가(유일)
- enroll_date : 중복 가능
- status : 중복 가능(수강중/취소/완료)
- semester : 중복 가능
- enroll_type : 중복 가능(정규/재수강)
- ※ (stuid, lid, semester) 조합은 UNIQUE → 한 학생이 같은 학기 같은 강의 중복 신청 불가

■ 성적(Grade) — 기본키: gradeid
- gradeid : 기본키, 중복 불가(유일)
- score : 중복 가능
- grade_letter : 중복 가능(같은 등급 다수)
- evaluation_date : 중복 가능
- remark : 중복 가능
- ※ enrollid(FK)는 UNIQUE → 수강신청 1건당 성적 1건(1:1)

## 2. 논리적 모델링 (관계 데이터 모델로의 매핑)

[요소2] 관계대응수에 맞는 외래키/대리키 삽입 및 참조 관계 서술

(밑줄=PK, * =FK)

```
Dept(deptid, dname, college, office, tel)
Professor(pid, pname, prof_rank, email, office, *deptid)
Student(stuid, sname, stu_year, phone, email, *deptid, *advisor_pid)
Lecture(lid, lname, lnum, credit, semester, *pid)
Enrollment(enrollid, *stuid, *lid, enroll_date, status, semester, enroll_type)
Grade(gradeid, *enrollid, score, grade_letter, evaluation_date, remark)
```

■ 관계별 외래키(FK) 삽입 설명
- R-7 belong (Student N:1 Dept): Student.deptid(FK)는 Dept(deptid)를 참조한다. N:1 관계라 N쪽
  (Student)에 외래키를 추가하여 학생의 소속 학과를 표현한다.
- R-8 work_dept (Professor N:1 Dept): Professor.deptid(FK)는 Dept(deptid)를 참조한다. 교수 소속 학과 표현.
- R-9 tutor (Professor 1:N Student): Student.advisor_pid(FK)는 Professor(pid)를 참조한다. N쪽(Student)에
  외래키를 추가하며, 지도교수 미배정을 허용하기 위해 NULL을 허용한다.
- R-10 manage (Professor 1:N Lecture): Lecture.pid(FK)는 Professor(pid)를 참조한다. 강의 담당 교수 표현.
- R-11 study (Student M:N Lecture): 다대다 관계이므로 교차 테이블 Enrollment를 생성하고,
  Enrollment.stuid(FK)→Student, Enrollment.lid(FK)→Lecture 두 개의 외래키로 분해한다.
- R-12 evaluate (Enrollment 1:1 Grade): Grade.enrollid(FK)는 Enrollment(enrollid)를 참조하며,
  enrollid에 UNIQUE를 부여하여 1:1 관계를 보장한다.

## 3. 종속성 판단 및 정규화 과정

[요소3] 각 릴레이션의 함수 종속성 명시

■ 함수 종속성 (X → Y : X가 Y를 결정)
- Dept    : deptid → dname, college, office, tel  /  dname → deptid (dname UNIQUE)
           → 후보키 {deptid}, {dname}
- Professor: pid → pname, prof_rank, email, office, deptid  /  email → pid (email UNIQUE)
           → 후보키 {pid}, {email}
- Student : stuid → sname, stu_year, phone, email, deptid, advisor_pid  /  email → stuid
           → 후보키 {stuid}, {email}
- Lecture : lid → lname, lnum, credit, semester, pid  → 후보키 {lid}
- Enrollment: enrollid → stuid, lid, enroll_date, status, semester, enroll_type
            /  (stuid, lid, semester) → enrollid  → 후보키 {enrollid}, {stuid,lid,semester}
- Grade   : gradeid → enrollid, score, grade_letter, evaluation_date, remark  /  enrollid → gradeid
           → 후보키 {gradeid}, {enrollid}

■ 정규화 (BCNF까지)
- 1NF: 모든 속성이 원자값(다치/복합 속성 없음). 충족.
- 2NF: 복합키 후보(Enrollment)에서도 비키 속성이 전체 키에 완전 종속. 부분 종속 없음. 충족.
- 3NF: 비키 → 비키 형태의 이행 종속 없음. 충족.
- BCNF: 위 함수 종속성 분석에서 모든 결정자가 후보키임을 확인 → 충족(3NF 포함).

■ 정규화 사례 (비정규 → 정규)
모든 정보를 한 테이블에 몰아넣은 BigEnroll(stuid, sname, deptid, dname, college, lid, lname, pid,
pname, score, grade_letter, semester)을 가정하면,
  deptid → dname, college (이행 종속),  pid → pname (이행 종속) 이 존재하여
  ① 삽입 이상(수강생 없는 신설 학과 등록 불가), ② 삭제 이상(마지막 행 삭제 시 학과명 소실),
  ③ 갱신 이상(학과명 변경 시 다수 행 수정 필요)이 발생한다.
이를 결정자별 테이블(Dept, Professor, Student, Lecture, Enrollment, Grade)로 분해하여 이행 종속을
제거하였으며, 분해는 무손실 조인과 함수 종속 보존을 만족한다.

### 4-2. 테이블 생성 (부모 → 자식 순)

```sql
CREATE TABLE Dept (
  deptid  INT AUTO_INCREMENT PRIMARY KEY,
  dname   VARCHAR(50) NOT NULL,
  college VARCHAR(50) NOT NULL,
  office  VARCHAR(50),
  tel     VARCHAR(20),
  CONSTRAINT uq_dept_name UNIQUE (dname)
) ENGINE=InnoDB;

CREATE TABLE Professor (
  pid       INT AUTO_INCREMENT PRIMARY KEY,
  pname     VARCHAR(30) NOT NULL,
  prof_rank VARCHAR(20) NOT NULL,
  email     VARCHAR(100),
  office    VARCHAR(50),
  deptid    INT NOT NULL,
  CONSTRAINT uq_prof_email UNIQUE (email),
  CONSTRAINT fk_prof_dept FOREIGN KEY (deptid) REFERENCES Dept(deptid)
      ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB;

CREATE TABLE Student (
  stuid       INT AUTO_INCREMENT PRIMARY KEY,
  sname       VARCHAR(30) NOT NULL,
  stu_year    TINYINT NOT NULL,
  phone       VARCHAR(20),
  email       VARCHAR(100),
  deptid      INT NOT NULL,
  advisor_pid INT,
  CONSTRAINT uq_stu_email UNIQUE (email),
  CONSTRAINT chk_stu_year CHECK (stu_year BETWEEN 1 AND 4),
  CONSTRAINT fk_stu_dept FOREIGN KEY (deptid) REFERENCES Dept(deptid)
      ON DELETE RESTRICT ON UPDATE CASCADE,
  CONSTRAINT fk_stu_advisor FOREIGN KEY (advisor_pid) REFERENCES Professor(pid)
      ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE=InnoDB;

CREATE TABLE Lecture (
  lid      INT AUTO_INCREMENT PRIMARY KEY,
  lname    VARCHAR(60) NOT NULL,
  lnum     VARCHAR(20) NOT NULL,
  credit   TINYINT NOT NULL,
  semester VARCHAR(10) NOT NULL,
  pid      INT NOT NULL,
  CONSTRAINT chk_lec_credit CHECK (credit BETWEEN 1 AND 3),
  CONSTRAINT fk_lec_prof FOREIGN KEY (pid) REFERENCES Professor(pid)
      ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB;

CREATE TABLE Enrollment (
  enrollid    INT AUTO_INCREMENT PRIMARY KEY,
  stuid       INT NOT NULL,
  lid         INT NOT NULL,
  enroll_date DATE NOT NULL DEFAULT (CURRENT_DATE),
  status      ENUM('수강중','취소','완료') NOT NULL DEFAULT '수강중',
  semester    VARCHAR(10) NOT NULL,
  enroll_type ENUM('정규','재수강') NOT NULL DEFAULT '정규',
  CONSTRAINT fk_enr_stu FOREIGN KEY (stuid) REFERENCES Student(stuid)
      ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT fk_enr_lec FOREIGN KEY (lid) REFERENCES Lecture(lid)
      ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT uq_enroll UNIQUE (stuid, lid, semester)
) ENGINE=InnoDB;

CREATE TABLE Grade (
  gradeid         INT AUTO_INCREMENT PRIMARY KEY,
  enrollid        INT NOT NULL,
  score           DECIMAL(5,2) NOT NULL,
  grade_letter    VARCHAR(2),
  evaluation_date DATE,
  remark          VARCHAR(100),
  CONSTRAINT uq_grade_enroll UNIQUE (enrollid),
  CONSTRAINT chk_grade_score CHECK (score >= 0 AND score <= 100),
  CONSTRAINT fk_grade_enr FOREIGN KEY (enrollid) REFERENCES Enrollment(enrollid)
      ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB;
```

■ 무결성 판단
- 개체 무결성: 모든 테이블 PK NOT NULL + 유일.
- 참조 무결성: FK 7개 + ON DELETE(RESTRICT/SET NULL/CASCADE) 규칙으로 보장.
- 도메인 무결성: CHECK(점수 0~100, 학년 1~4, 학점 1~3), ENUM(상태·신청구분).
- 키 무결성: UNIQUE(dname, email, (stuid,lid,semester), enrollid).
- (검증) 없는 학과로 학생 삽입 시 FK 오류(1452), 점수 150 삽입 시 CHECK 오류(3819),
  중복 신청 시 UNIQUE 오류(1062)로 거부됨을 확인하였다.

## 6. (추가 구현) 고급 기능 및 성능 최적화  ※ 가점 요소, optimization.sql 참조

- View: StudentGradeView(학생 성적표), LectureStatView(강의별 통계)
- Stored Procedure: GetStudentGrade(학번) → 성적 상세 + 평균/학점/GPA 반환
- Transaction: 수강신청+성적 입력을 COMMIT/ROLLBACK/SAVEPOINT로 원자 처리
- Index: idx_student_name, idx_lecture_name 등 생성
- 성능 실험: 학생 1만·강의 1천·수강 5만·성적 5만 건 생성 후, 이름 검색 질의를 인덱스 전/후로
